## 修复空表格单元格被压塌

- 用户截图：刚插入的全空表格行高明显小于填了内容之后，视觉上差太多。
- 根因：空单元格没有任何行盒，高度只剩 `padding: 7px 12px`（15px）；
  有内容时多出一行 line-height（41.3px）。`table-cell` 上 `min-height` 不生效，
  给 `th/td` 设 `height` 会把有内容的行也一起撑高，改变既有排版。
- 方案：`widgets.js` 的 `buildRow` 给 `c.text` 为空的格子打 `is-empty` class；
  `base.css` 用 `.cm-table-wrap .is-empty::after { content: "\200b" }` 补一个零宽文本行。
  高度自动跟随主题 font-size / line-height；伪元素内容不属于 DOM 文本节点，
  不污染 `textContent`、选中复制与单元格就地编辑。
- 为什么不用 `:empty`：表头 `th` 里恒有 `.cm-table-resize` 拖拽手柄，`:empty` 不匹配，
  实测只有数据行被撑高、表头仍矮 15px。
- 量化（真实应用 iframe + `?debug=1`）：修复前空行 15px / 有内容 41.3px，差 26.3px；
  修复后两者都是 41.3px，表头与数据行都一致。端到端断言 10/10。
- 测试文档注意：`scanTables` 会把「表格中间单个空行」并入同一张表，
  两个表格之间必须放一段普通正文，否则会合并成一个 widget。
- iframe 测试注意：必须在 iframe 导航完成后再取 `contentDocument`，
  否则拿到的是 about:blank 的文档（表现为 `editor=false`、`lines=0`）。
- Vite 构建到临时目录通过。

## 根治：文件/系统对话框阻塞主线程导致卡死

- 用户反馈：新建文档输入内容 → Ctrl+S → 选文件夹后界面冻结，只能强杀重开。
- 根因：`src-tauri/src/lib.rs` 里 `file_save_as` 是**同步命令**，内部调用
  `.blocking_save_file()`。Tauri v2 同步命令在 WebView UI 线程内联执行，
  blocking_* 会 park 这个线程等回调，而回调又依赖同一消息循环派发 → 永久冻结。
  前端 Ctrl+S 位于 `runtime.js:501` → `save():3210` → `saveAs():3247` → `studio.saveAsDialog`。
- 关键线索：项目 `exports.rs:139-161` 的 `save_dialog()` 早已为导出功能写好正确范式
  （回调式 `.save_file()` + `spawn_blocking(rx.recv())`），并留有注释指出 blocking_* 的危害；
  另存为路径漏改。
- 修复：把 `file_open`、`settings_import_pick`、`file_save_as`、`dialog_confirm`、
  `dialog_unsaved`、`dialog_info` 全部改为 `async fn` + 回调式 API + `spawn_blocking` 等待；
  落盘 IO 也放进 `spawn_blocking`（含 fsync，慢盘不该卡 UI）。
  `file_save_as` 保留双 filter（md / markdown），未复用 save_dialog 的单扩展名签名。
- 验证：`cargo check` 通过（6 个命令签名变更，命令注册表无需改动）。
- 注意：此前「粘贴图片卡死」改用应用内面板绕开 confirm，现在原生 confirm 已非阻塞，
  但应用内面板体验更好，保留不回退。遗留：`askText()`（runtime.js:939）关闭面板时
  Promise 不 settle，仍可能挂起调用方，不在本次 bug 路径。
